# Multi-Agent Communication Architectures, Agentic RAG, and AI Agent Evaluation Frameworks

## What real, documented multi-agent orchestration patterns exist for agents communicating/collaborating to improve output? (debate, supervisor-worker, blackboard, named frameworks)

### Takeaway
There are a handful of named, real patterns with actual implementations: **group-chat/debate** (AutoGen's AgentChat, and the academic "multi-agent debate" method), **supervisor-worker/hierarchical handoff** (LangGraph's `langgraph-supervisor`, CrewAI's hierarchical process), and **blackboard** (a shared-state architecture, mostly research-stage for LLM agents, with one open-source project). Of the three big named frameworks, **AutoGen is archived/unmaintained** (Microsoft redirects new users elsewhere), while **CrewAI and LangGraph are active** with large repos and real adoption.

### Cited Findings
- **AutoGen (Microsoft) is archived and unmaintained.** Its README states: "Project archived and no longer maintained," "Microsoft is not providing bug fixes, security fixes, new features, or support for this project," and "New users should start with Microsoft Agent Framework." Remaining contributions are limited to bug fixes, security patches, and documentation. — [github.com/microsoft/autogen](https://github.com/microsoft/autogen)
- AutoGen's AgentChat API supported "common multi-agent patterns such as two-agent chat or group chats," where a group chat manager determines who speaks next; its Core API handled message passing and event-driven agents; **Magentic-One** was AutoGen's example multi-agent team built on AgentChat/Extensions. — [github.com/microsoft/autogen](https://github.com/microsoft/autogen)
- Microsoft Agent Framework (the successor AutoGen now points to) is MIT-licensed, has Python/C# parity, and ships orchestration patterns: sequential, concurrent, handoff, and group collaboration. — [spheron.network](https://www.spheron.network/blog/langgraph-vs-crewai-vs-autogen-2026/), [futureagi.com](https://futureagi.com/blog/crewai-vs-langgraph-vs-autogen-2026) (secondary/vendor sources, not independently verified against Microsoft's own docs in this pass)
- **CrewAI** is an open-source Python framework "for orchestrating role-playing, autonomous AI agents," with 60.1k GitHub stars, 8.9k forks, 393 watchers, and 3,047 commits on main (snapshot at research time). It supports **Crews** (role-based agent teams with "dynamic task delegation and collaboration" and "specialized roles with defined goals and expertise"), a **hierarchical process** where a manager agent is automatically assigned to coordinate planning, delegate tasks, and validate results, and a **sequential process**. Its 2025-added **Flows** layer uses `@start`, `@listen`, and `@router` decorators for deterministic control flow, letting a Flow call Crews as steps requiring autonomous reasoning. — [github.com/crewAIInc/crewAI](https://github.com/crewAIInc/crewAI); decorator/Flow detail also at [softwareseni.com](https://www.softwareseni.com/navigating-the-multi-agent-framework-landscape-from-crewai-to-langgraph-to-autogen-and-beyond)
- **LangGraph** (LangChain) is a "low-level orchestration framework for building stateful agents," MIT-licensed, with ~7,211 commits on main, 43.8k stars, 7.5k forks, 189 watchers, 356 open issues (snapshot at research time). It is explicitly tagged "multiagent" and points to **Deep Agents**, a higher-level package built on LangGraph that can use subagents. — [github.com/langchain-ai/langgraph](https://github.com/langchain-ai/langgraph)
- **Supervisor-worker pattern, concretely implemented:** the `langgraph-supervisor` Python package provides `create_supervisor()` (a central agent that routes work to specialized worker agents) and `create_handoff_tool()` (delegation via a tool call). The default handoff tool is named `transfer_to_<agent_name>` with description "Ask agent `<agent_name>` for help." An `output_mode` setting controls whether the supervisor sees a worker's `full_history` or just its `last_message` (default). Nested hierarchies are supported — a top-level supervisor can manage multiple sub-supervisors, each compiled with a name. — [LangGraph supervisor docs / PyPI](https://pypi.org/project/langgraph-supervisor/), [reference.langchain.com](https://reference.langchain.com/python/langgraph/supervisor)
- LangGraph's official multi-agent custom guide frames a **handoff** as a primitive describing which agent to hand control to plus the payload to send it, implemented via `Send()` to pass a task description, or via tool-based `Command` returns in the prebuilt agent/`ToolNode`. — [docs.langchain.com/oss/python/multi-agent-custom](https://docs.langchain.com/oss/python/multi-agent-custom)
- Coordination-style differences across frameworks: LangGraph uses an explicit-edge graph, CrewAI uses a role hierarchy with a supervisor, AutoGen used group chat with a manager deciding the next speaker. — [raftlabs.com](https://www.raftlabs.com/blog/ai-orchestration-platform-guide), [softwareseni.com](https://www.softwareseni.com/navigating-the-multi-agent-framework-landscape-from-crewai-to-langgraph-to-autogen-and-beyond) (vendor/blog sources; directional, not verified against primary docs)
- **Multi-agent debate (academic, real implementation):** Du, Li, Torralba, Tenenbaum, and Mordatch (MIT CSAIL / Google Brain), "Improving Factuality and Reasoning in Language Models through Multiagent Debate," ICML 2024, arXiv:2305.14325 (first posted May 2023). Multiple LLM instances independently propose answers, then review each other's responses over several rounds until converging. The authors report the method improves mathematical and strategic reasoning across tasks (biography generation, MMLU, chess move validity/optimality, arithmetic, grade-school math) and reduces inclusion of facts the model was internally uncertain about, because disagreeing instances tend to drop those facts. — [arXiv:2305.14325](https://arxiv.org/pdf/2305.14325), [PMLR/ICML 2024](https://proceedings.mlr.press/v235/du24e.html)
- **Blackboard architecture for LLM agents (research-stage):** Han and Zhang, arXiv:2507.01701, "Exploring Advanced LLM Multi-Agent Systems Based on Blackboard Architecture" — agents see the full shared state on a blackboard, the next acting agent is chosen based on current blackboard contents, and a select-and-act loop repeats until consensus. The authors claim this is the first such implementation and report competitive results against SOTA static/dynamic multi-agent systems while using fewer tokens, tested on commonsense, reasoning, and math datasets. — [arxiv.org/html/2507.01701v1](https://arxiv.org/html/2507.01701v1)
- An open-source project called **bmas** (found via an ecosyste.ms listing) coordinates LLM agents through a shared blackboard, with a stack of FastAPI, Redis, Docker Compose, and llama.cpp. — [awesome.ecosyste.ms/projects/github.com%2Farvarik%2Fbmas](https://awesome.ecosyste.ms/projects/github.com%2Farvarik%2Fbmas) (could not independently verify repo activity/maintenance in this pass)
- Older, non-LLM blackboard work exists for context: a 2006 avionics paper describes a distributed blackboard with rule-based event notification for peer-to-peer agent sharing, and an IBM paper (2005) combines blackboard with implicit invocation to decouple control policy from the shared repository. — [icas.org ICAS2006 paper](https://icas.org/ICAS_ARCHIVE/ICAS2006/PAPERS/488.PDF), [IBM research paper](https://researchweb.draco.res.ibm.com/publications/event-based-blackboard-architecture-for-multi-agent-systems)
- Multiple 2026 vendor/blog comparisons converge on **five common production orchestration patterns**: sequential, concurrent, group chat, handoff, and "plan-first" (Magentic-style), and note that most production teams combine a thin framework layer with custom workflow logic rather than committing fully to one framework; OpenTelemetry-compatible tracing is cited as a converging observability standard across these runtimes. — [raftlabs.com](https://www.raftlabs.com/blog/ai-orchestration-platform-guide), [futureagi.com](https://futureagi.com/blog/crewai-vs-langgraph-vs-autogen-2026), [businesstechnavigator.com](https://businesstechnavigator.com/blog/langgraph-vs-crewai-vs-autogen-production-2026) (vendor/blog sources — directional, treat cautiously)

### Inferences
- The field has consolidated around two live, well-adopted frameworks for real multi-agent orchestration — **LangGraph** (graph/handoff-based, with the `langgraph-supervisor` package for hierarchical supervisor-worker) and **CrewAI** (role-based crews + deterministic Flows) — while **AutoGen is a dead end for new projects** per Microsoft's own archive notice.

## What is "agentic RAG" specifically (vs. plain RAG), and what are the leading real implementations/repos?

### Takeaway
Agentic RAG means inserting agent-style decision-making (planning, tool/retrieval choice, self-grading, iteration) into the RAG loop, rather than a fixed one-shot retrieve-then-generate chain. The most concrete, primary-source implementation is **LangChain/LangGraph's official "Build a custom RAG agent with LangGraph" tutorial**, which wraps a retriever as a callable tool and lets the model decide whether to call it, then grades/corrects retrieved documents.

### Cited Findings
- Definition (vendor/glossary consensus): agentic RAG "incorporates AI agents into the RAG pipeline to orchestrate its components and perform additional actions beyond simple information retrieval and generation," or equivalently, inserts "a planning and self-evaluation step" into a typical RAG pipeline, making retrieval iterative rather than one-shot. — [weaviate.io/blog/what-is-agentic-rag](https://weaviate.io/blog/what-is-agentic-rag), [flowhunt.io/glossary/agentic-rag](https://flowhunt.io/glossary/agentic-rag)
- **Primary, official implementation:** LangChain's docs ship "Build a custom RAG agent with LangGraph" (Python and JS). It indexes documents, wraps the retriever as a tool, and builds an agent where a `generate_query_or_respond` node binds the retriever tool via `.bind_tools` — the model decides whether to retrieve or answer directly, and retrieval only runs when the model requests it. Later steps in the tutorial add document grading (i.e., checking retrieved docs are actually relevant before generating). LangChain's docs explicitly distinguish this from their built-in prebuilt agents (also implemented via LangGraph primitives) for cases needing deeper customization. — [docs.langchain.com/oss/python/langgraph/agentic-rag](https://docs.langchain.com/oss/python/langgraph/agentic-rag)
- Related named variants built on the same idea: **Adaptive RAG**, **Corrective RAG (CRAG)**, and **Self-RAG** — one community guide combines all three in a local agent using Llama 3 (via Ollama) plus Tavily web search, and Elastic publishes a LangGraph retrieval-agent template integrated with LangChain. — [leanware.co/insights/langgraph-rag-agentic](https://leanware.co/insights/langgraph-rag-agentic) (secondary source; directional)
- Frameworks/tools named across multiple glossary sources as providing templates for agentic RAG: **LangChain, CrewAI, DSPy, and FlowHunt**. One guide also recommends giving the agent an explicit tool to grade/score retrieved documents, and recommends a staged rollout rather than over-engineering the first iteration. — [softwebsolutions.com agentic-rag guide](https://www.softwebsolutions.com/resources/agentic-rag-types-and-implementation-guide/), [ampcome.com agentic-rag post](https://www.ampcome.com/post/agentic-rag-meaning-types-examples-and-implementation)
- Trade-off noted by vendor sources: agentic RAG is suited to cases "when intelligence and adaptability matter more than speed and cost," and teams need to monitor retrieval quality, tool accuracy, step efficiency, and faithfulness as ongoing metrics (this links directly to the evaluation section below — DeepEval has metrics named exactly for this: `StepEfficiencyMetric`, `Faithfulness`, retrieval-quality metrics). — [softwebsolutions.com](https://www.softwebsolutions.com/resources/agentic-rag-types-and-implementation-guide/)

### Inferences
- Agentic RAG is less a single named framework and more a design pattern implementable in any agent framework that supports tool-calling (LangGraph being the most directly documented, official example found in this research).
- The LangGraph agentic-RAG tutorial and the DeepEval component-level tracing scheme (retriever spans, `next_retriever_span`) are complementary — i.e., a LangGraph agentic RAG pipeline is a natural fit for DeepEval's "Faithfulness"/retrieval-quality metrics described in the evaluation section.

### Gaps
- Most sources describing "types" of agentic RAG (vendor glossaries from Weaviate, FlowHunt, Softweb, Ampcome, Coursera, Mem0) overlap heavily and are not primary/original sources — treat the taxonomy ("types of agentic RAG") as descriptive marketing content rather than a settled technical standard.
- Did not independently verify the LlamaIndex agentic-RAG implementation (not fetched directly in this pass) despite LlamaIndex appearing in DeepEval integration search results — worth checking `developers.llamaindex.ai` docs directly if LlamaIndex specifically is in scope.

## How is DeepEval actually used in practice, including LangChain integration? What metrics/workflows does it provide for evaluating agent behavior over time?

### Takeaway
DeepEval integrates with LangChain via a **CallbackHandler** passed into the agent's `invoke` config, which traces runs as a tree of spans (agent/LLM/tool/retriever); the officially documented LangChain-callback path currently supports **TaskCompletionMetric** as the main metric, while deeper/other metrics require manual `@observe` instrumentation rather than the callback alone. DeepEval's broader workflow (independent of LangChain specifically) is: build a golden dataset → instrument with `@observe` → iterate in dev via `evals_iterator` → gate CI with `assert_test`/`deepeval test run` (pytest-style) → inspect traces with `deepeval inspect` → optionally feed production failures back from Confident AI into new goldens.

### Cited Findings
- **Setup (Python):** import `CallbackHandler` from `deepeval.integrations.langchain`, pass via `config={"callbacks": [CallbackHandler()]}` on the agent's `invoke` call; **TypeScript** equivalent is `DeepEvalCallbackHandler` from `deepeval/integrations/langchain`, passed as `{ callbacks: [handler] }`. Install via `pip install -U deepeval langchain langchain-openai` or `npm install -D deepeval langchain @langchain/core @langchain/openai`. — [deepeval.com/integrations/frameworks/langchain](https://deepeval.com/integrations/frameworks/langchain)
- Each traced run produces spans for **agent, LLM, tool, and retriever** components — i.e., component-level visibility, not just a final input/output pair. — [deepeval.com/integrations/frameworks/langchain](https://deepeval.com/integrations/frameworks/langchain)
- The official LangChain integration page states metrics shown in examples include **TaskCompletionMetric, StepEfficiencyMetric, PlanAdherenceMetric** (trajectory-level, i.e. scoring the whole sequence of spans, not just the final output), plus general-purpose **G-Eval, Faithfulness, and AnswerRelevancyMetric**. — [deepeval.com/integrations/frameworks/langchain](https://deepeval.com/integrations/frameworks/langchain)
- Component-level staging functions exist to attach a metric to the *next* matching span: `next_agent_span`, `next_llm_span`, `next_retriever_span` (Python), plus `nextToolSpan` (TypeScript). Note: `next_llm_span` is one-shot — it only applies to the first LLM span in a run; for scope-wide application across every matching span, use `trace(llm_span_context=...)` (Python) or `setTracingContext` (TypeScript). Tools can be scored via a patched `tool` decorator accepting `metric_collection` (Python) or `updateCurrentSpan` inside the tool body (TypeScript). — [deepeval.com/integrations/frameworks/langchain](https://deepeval.com/integrations/frameworks/langchain)
- The page recommends attaching metrics at the LLM or trace level rather than directly on tools, and states the only version pairing it explicitly tested was `@langchain/core==1.1.31` with `deepeval==0.9.11` (TypeScript) — i.e., broader historical version compatibility is **not** guaranteed/documented. — [deepeval.com/integrations/frameworks/langchain](https://deepeval.com/integrations/frameworks/langchain)
- **CI/CD workflow:** in Python, `assert_test(golden=golden, metrics=[...])` plus `deepeval test run` run as pytest, failing the build on a failing metric on every push/PR; TypeScript equivalent is `expect(golden).toPass(...)` with `npx deepeval test run`. For dev-loop iteration (not CI gating), use `dataset.evals_iterator(metrics=[...])` in a script/notebook — and the docs recommend `evals_iterator` over passing `metrics` directly to the CallbackHandler for eval scripts. — [deepeval.com/integrations/frameworks/langchain](https://deepeval.com/integrations/frameworks/langchain), [deepeval.com/docs/getting-started-agents](https://www.deepeval.com/docs/getting-started-agents)
- **Full agent-evaluation workflow** per DeepEval's "getting started agents" doc: (1) create a dataset of "goldens" (inputs to invoke the agent with — defined in code, pulled from Confident AI, or loaded from CSV/JSON); (2) instrument the agent with `@observe` or a framework integration so each run emits a trace with spans for LLM calls, tools, retrievers, sub-agents; (3) iterate during development with `dataset.evals_iterator(metrics=[...])`; (4) unit test in CI/CD with `assert_test` + `deepeval test run`; (5) inspect results with `deepeval inspect`, which shows the trace tree with per-span scores and metric reasons, saved locally and optionally sent to Confident AI; (6) feed production failures back — Confident AI surfaces failing production traces and can turn them into new goldens for future evals. — [deepeval.com/docs/getting-started-agents](https://www.deepeval.com/docs/getting-started-agents)
- Agents should be evaluated **both end-to-end** (metrics attached to the whole trace via `assert_test`/`evals_iterator`) **and at the component level** (metrics attached to individual spans, e.g. `@observe(type="agent", metrics=[...])` for sub-agents, or staged via `next_agent_span(...)`); for raw OpenAI/Anthropic clients that emit only LLM spans, use `LlmSpanContext` to target them. — [deepeval.com/docs/getting-started-agents](https://www.deepeval.com/docs/getting-started-agents)
- Note on source conflict: a third-party Tessl mirror of DeepEval's docs shows the `CallbackHandler` constructor taking a `metrics=` argument directly, while the current official page and DeepEval 4.0 blog construct `CallbackHandler()` with no arguments and apply metrics via `evals_iterator`/`assert_test` instead; the official examples also differ on which LangChain agent constructor to use (`create_tool_calling_agent` vs. `create_agent`). **This suggests the API has changed across DeepEval versions** — the current official `deepeval.com` pages should be treated as authoritative over the Tessl mirror, and the installed version's actual API should be checked before relying on either. — [tessl.io mirror](https://tessl.io/registry/tessl/pypi-deepeval/files/docs/integrations.md) vs. [deepeval.com/integrations/frameworks/langchain](https://deepeval.com/integrations/frameworks/langchain)
- DeepEval's own comparison blog claims it offers "everything Ragas offers but more, including agentic and chatbot evaluations" (self-interested vendor claim, flagged as such). A third-party comparison describes DeepEval as shipping test cases, assertions, 40+ metrics, G-Eval, DAG (a decision-graph style custom metric), red-teaming, and a hosted dashboard via Confident AI. — [deepeval.com/blog/deepeval-vs-ragas](https://www.deepeval.com/blog/deepeval-vs-ragas) (vendor source — self-comparison, treat accordingly)

### Inferences
- DeepEval is explicitly designed as a **pytest-style, CI-gatable** evaluation framework with trace/span-level granularity — its core value-add over a plain "LLM-as-judge on final output" approach is scoring intermediate steps (tool calls, retrieval, individual agent hops) and failing a build on regressions, which maps directly onto evaluating multi-agent systems (each agent/hop = a span that can carry its own metric).
- The LangChain callback integration is a thinner/simpler ingestion path than full manual `@observe` instrumentation, and is best suited to getting `TaskCompletionMetric` (end-to-end) quickly; for the richer trajectory metrics (`StepEfficiencyMetric`, `PlanAdherenceMetric`) and tool-level scoring, manual instrumentation appears to be the documented path, though the LangChain-integration page itself also lists these metrics in its examples — the exact division of "what the callback alone can score" vs. "what requires `@observe`" was not fully disambiguated in the fetched page content (see Gaps).

## Are there other notable AI agent evaluation frameworks worth knowing about alongside DeepEval?

### Takeaway
Besides DeepEval, the most cited frameworks are **Ragas** (RAG-focused but with some agent metrics), **Arize Phoenix** and **Langfuse** (open-source, OpenTelemetry-based tracing + eval), and **LangSmith** (proprietary, LangChain/LangGraph-native). Vendor-neutral sources note the eval/observability vendor space has seen real consolidation risk (acquisitions/shutdowns), which should factor into any adoption decision.

### Cited Findings
- **Ragas:** per a secondary citation of MLflow's 2026 agent evaluation guide, Ragas provides "research-validated metrics for faithfulness, answer relevancy, context precision, agent goal accuracy, and tool call accuracy" — i.e., it does have some agent-specific metrics (goal accuracy, tool-call accuracy) beyond pure RAG metrics, though its catalog is still described as fundamentally "RAG-shaped." — [keywordsai.co/market-map/compare/deepeval-vs-ragas](https://keywordsai.co/market-map/compare/deepeval-vs-ragas) (secondary source, not Ragas's own docs — not independently verified against Ragas's primary repo in this pass)
- **Workflow difference vs. DeepEval:** Ragas works in batch mode and reports per-metric averages (suited to tracking quality trends over time); DeepEval gives a pass/fail verdict per test case and integrates with pytest (suited to CI gating). Both rely on LLM-as-a-judge under the hood, incurring judge-model token cost in both cases. — [dev.to/wonderlab DeepEval-in-practice writeup](https://dev.to/wonderlab/ai-evaluation-series-06-deepeval-in-practice-enterprise-agent-evaluation-suite-22c)
- **Arize Phoenix:** described across sources as fully open source and self-hostable, built on OpenTelemetry standards, with **trajectory evaluation** (scores path quality, not just final output), tool-usage analysis, and session-level online evaluation. — [docs.arize.com/phoenix FAQ](https://docs.arize.com/phoenix/learn/resources/faqs/langsmith-alternatives), [getmaxim.ai comparison](https://getmaxim.ai/articles/choosing-the-right-ai-evaluation-and-observability-platform-an-in-depth-comparison-of-maxim-ai-arize-phoenix-langfuse-and-langsmith)
- **Langfuse:** MIT-licensed, aimed at teams willing to self-host; offers tracing, prompt management, and evals, though one comparison characterizes its evaluation depth as "basic"/thinner than Phoenix's. — [getmaxim.ai comparison](https://getmaxim.ai/articles/choosing-the-right-ai-evaluation-and-observability-platform-an-in-depth-comparison-of-maxim-ai-arize-phoenix-langfuse-and-langsmith)
- **LangSmith:** proprietary SaaS (LangChain and LangGraph themselves are open source, but LangSmith is not); self-hosting is a paid feature (vs. free for Phoenix). Its agent evaluation includes a "multi-turn evaluation framework" checking whether an agent met a user's goal across a whole conversation. Best fit cited for teams already standardized on LangChain/LangGraph. — [docs.arize.com/phoenix FAQ](https://docs.arize.com/phoenix/learn/resources/faqs/langsmith-alternatives)
- **Vendor stability warning (important for adoption decisions):** an Atlan guide flags that **Humanloop, Weights & Biases, Langfuse, and Galileo** have each been "acquired or shut down as independent companies within roughly a year" (as reported in that guide) — meaning vendor durability is a real selection factor in this space, not just features. — [atlan.com best-ai-agent-evaluation-platforms](https://atlan.com/know/ai-agent/ai-agent-evals/best-ai-agent-evaluation-platforms/) (single source for this specific claim — could not cross-verify independently; treat as a flag to investigate rather than settled fact, especially since Langfuse is cited as both "shut down" by this source and as an active MIT tool by others — **direct contradiction**, noted explicitly here)
- Atlan's guide also reports **5 open-source options** in this space: **Arize Phoenix, Comet Opik, Confident AI/DeepEval, MLflow, and Langfuse**, with paid tiers (where published) ranging from free up to $2,499+/month across the broader platform set. — [atlan.com best-ai-agent-evaluation-platforms](https://atlan.com/know/ai-agent/ai-agent-evals/best-ai-agent-evaluation-platforms/)
- A recurring theme across multiple 2026 comparison pieces: standard LLM eval frameworks tend to evaluate **final outputs**, not **trajectories** (the full sequence of steps/tool calls an agent took), and several sources explicitly recommend picking a framework that is "trajectory-first" if evaluating multi-step agent behavior is the goal (this favors DeepEval's trace/span approach and Arize Phoenix's trajectory scoring over simpler output-only judges). — [morphllm.com/ai-agent-evaluation-frameworks](https://www.morphllm.com/ai-agent-evaluation-frameworks), [latitude.so best-ai-agent-evaluation-platforms-2026](https://latitude.so/blog/best-ai-agent-evaluation-platforms-2026-comprehensive-comparison)
