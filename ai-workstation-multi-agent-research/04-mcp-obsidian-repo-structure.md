## What are the most useful/popular MCP servers for a personal AI workstation (filesystem, memory/knowledge, web search, git)? Which are well-maintained as of 2026?

### Takeaway
The official `modelcontextprotocol/servers` repo keeps only a small set of reference servers alive in 2026 (Everything, Fetch, Filesystem, Git, Memory, Sequential Thinking, Time) — most of the original 2024 reference set (GitHub, GitLab, Slack, Postgres, Puppeteer, Redis, Sentry, Brave Search, Google Drive/Maps, AWS KB Retrieval, EverArt) was archived to `servers-archived` and superseded by vendor-maintained servers. For real workflows, people pair a small number of these reference servers with vendor-official servers (GitHub's own `github-mcp-server`, Brave's own `@brave/brave-search-mcp-server`) rather than the old community/reference ones.

### Cited Findings
- The official reference-server repo is `github.com/modelcontextprotocol/servers`, described in its README as housing only "the small number of reference servers maintained by the MCP steering group," with the full server ecosystem pointed to the MCP Registry instead — [modelcontextprotocol/servers](https://github.com/modelcontextprotocol/servers), [MCP Registry](https://registry.modelcontextprotocol.io/)
- Currently-maintained reference servers in that repo: **Everything** (test/reference server), **Fetch** (web content fetching/conversion for LLM use), **Filesystem** (file ops with configurable access controls), **Git** (read/search/manipulate local git repos), **Memory** (knowledge-graph-based persistent memory), **Sequential Thinking** (step-by-step reflective problem solving), **Time** (timezone conversion) — [modelcontextprotocol/servers](https://github.com/modelcontextprotocol/servers)
- Archived (moved to `servers-archived`) reference servers include AWS KB Retrieval, Brave Search (replaced by Brave's own official server), EverArt, GitHub, GitLab, Google Drive, Google Maps, PostgreSQL, Puppeteer, Redis, Sentry, Slack (now maintained by Zencoder), SQLite — [modelcontextprotocol/servers](https://github.com/modelcontextprotocol/servers)
- The Memory server stores entities, relations, and observations as a local knowledge graph, persisted to a JSONL file at a path set by the `MEMORY_FILE_PATH` env var; installed via `npx -y @modelcontextprotocol/server-memory`; tools include `create_entities`, `create_relations`, `add_observations`, `search_nodes`, `read_graph`, `open_nodes` — [Glama: Memory MCP architecture docs](https://glama.ai/mcp/servers/@danielsimonjr/memory-mcp/blob/615256e6bf38751a64d9de09f402c4ca4fdef568/docs/architecture/ARCHITECTURE.md) (third-party write-up; the official repo itself does not document internals in as much detail, so treat specifics as secondary-sourced even though the server's existence is primary-confirmed)
- Reviewers note the reference Memory server's graph model is simple — no built-in pruning, no UI, no conflict detection — pushing some users toward vector stores or richer community forks (e.g., a 59-tool enhanced version, an Elasticsearch-backed version) — [Glama Memory MCP docs](https://glama.ai/mcp/servers/@danielsimonjr/memory-mcp/blob/a979c4406d4be161e951adb033ee00ac1336ba99/docs/architecture/OVERVIEW.md)
- For GitHub work, the current recommended server is GitHub's own `github/github-mcp-server`, rewritten in Go and built jointly with Anthropic to replace the earlier community server; covers issues, PRs, code search, Actions, and security alerts; runs hosted or as a local binary; has a read-only mode that disables every write tool — [Morphllm: Git MCP Server guide](https://www.morphllm.com/git-mcp-server), [Scrimba: Best MCP Servers for Developers 2026](https://scrimba.com/articles/best-mcp-servers-for-developers-2026/)
- The separate reference **Git** server (`src/git` in modelcontextprotocol/servers) operates only on local repositories via the filesystem, not any remote API — it handles local commits/branches without touching GitHub — [Scrimba 2026 guide](https://scrimba.com/articles/best-mcp-servers-for-developers-2026/)
- For web search, Brave's current official server is the npm package `@brave/brave-search-mcp-server` (web/local/image/video/news search plus AI summarization, runs via npx or Docker), distinct from and superseding the older reference `@modelcontextprotocol/server-brave-search` — [Brave Search MCP listing](https://enterprisedna.co/directories/mcp/mcp-brave-search)
- Tavily publishes an official-style MCP server (`tavily-ai` account) offering search, extract, map, and crawl tools for advanced web search — [WebSearch result, unconfirmed primary source for exact repo name]
- A common "starter set" recommendation for 2026 is GitHub MCP + Context7 + Playwright, adding others only once a real workflow needs them, plus a caveat that Anthropic archived 13 of the original 20 reference servers in 2025 — so always check an "official" server is still maintained before adopting it — [Techsy: best MCP servers 2026](https://techsy.io/en/blog/best-mcp-servers-2026)
- Security guidance: use fine-grained personal access tokens with minimal scopes for any MCP server that touches an external account (GitHub, cloud, etc.) — [Olostep: best MCP servers](https://www.olostep.com/blog/best-mcp-servers)
- Anthropic's own Claude Code docs describe connecting MCP servers generically via `claude mcp add --transport http <name> <url>` (example given: Notion at `https://mcp.notion.com/mcp`), framed as the way to let Claude "implement features from issue trackers, query databases, analyze monitoring data, integrate designs from Figma, and automate workflows" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- For a personal multi-agent workstation, the practical "well-maintained, low-risk" stack as of 2026 looks like: reference **Filesystem** + **Git** + **Fetch** + **Sequential Thinking** + **Time** servers from the official repo for local/file/reasoning tasks, plus vendor-maintained servers (GitHub's own, Brave's own, or Tavily) layered on top for anything that talks to an external API — rather than relying on the archived reference servers for those external integrations.
- The reference **Memory** server is a reasonable starting point for simple entity/relation persistence, but its lack of pruning/conflict-detection means it's better suited to small, curated knowledge graphs than as a general-purpose "memory of everything" layer — this is likely why Obsidian-vault-based approaches (see next section) have emerged as an alternative for personal knowledge/memory specifically.

## Are there documented patterns/tools for using Obsidian as an AI agent's memory system, including techniques to make retrieval more token-efficient over time?

### Takeaway
Several real, working projects use a plain-markdown Obsidian vault as agent memory, splitting into roughly two camps: (1) simple MCP/REST bridges that let an agent read/write vault files directly using fixed folder paths and frontmatter as a lightweight schema (no embeddings), and (2) heavier stacks that add a vector/graph index (SQLite, DuckDB, pgvector) on top of the markdown for semantic retrieval. For token efficiency specifically, the most concretely documented technique is a memory-tiering scheme (working → episodic → semantic) with scheduled consolidation/summarization passes, combined with predictable folder paths and frontmatter fields so agents filter/reason without reading full file bodies.

### Cited Findings
- **MindStudio's "Claude Code + Obsidian" architecture** (closest documented match to the user's existing human/machine-split vault) uses: a dedicated `_agent/` folder with fixed subpaths (`memory/working/`, `memory/episodic/`, `memory/semantic/`, `skills/`, `heartbeat/`, `context/`) kept separate from personal content (`notes/`, `projects/`, `inbox/`); the article states predictable paths matter because an agent "hunting through an unstructured vault burns context on navigation" — [MindStudio: AI second brain Claude Code Obsidian architecture](https://www.mindstudio.ai/blog/ai-second-brain-claude-code-obsidian-architecture)
- Frontmatter convention in that architecture: `type` (concept/project/person/meeting/resource), `tags`, `created`, `last-reviewed`, `importance` (high/medium/low), and an `agent-written` boolean so humans can "distinguish what the system generated versus what you wrote" — [MindStudio article](https://www.mindstudio.ai/blog/ai-second-brain-claude-code-obsidian-architecture)
- Memory-tiering/consolidation pattern: working memory is session-scoped; files older than 48 hours move to episodic memory; episodic notes are short structured records (Context, Observations, Patterns, Links) written only for decisions/observations/patterns (not routine task completions); a scheduled "heartbeat" reviews recent episodes, extracts patterns, and writes conservative semantic notes that cite their supporting episodes; a weekly deep review looks back over a month of episodes — [MindStudio article](https://www.mindstudio.ai/blog/ai-second-brain-claude-code-obsidian-architecture)
- Token-efficiency techniques named explicitly: enforce hard context limits (unbounded context causes the agent to drop important information); "load a summary of semantic memory, not the full files"; use a dedicated context-loader skill that pulls only what's relevant to the current task; keep fixed paths + frontmatter specifically so the agent doesn't have to search — [MindStudio article](https://www.mindstudio.ai/blog/ai-second-brain-claude-code-obsidian-architecture)
- Retrieval mechanism in that architecture is plain keyword search via the **Obsidian Local REST API** community plugin (e.g., `POST /vault/search/simple`) plus direct path reads/writes — not embeddings. The article explicitly contrasts this with vector-database RAG, calling that approach "reactive and stateless" by comparison. Embeddings are mentioned only as a possible future addition for a "backlink analyzer" skill that would find unlinked notes by semantic similarity — no implementation given — [MindStudio article](https://www.mindstudio.ai/blog/ai-second-brain-claude-code-obsidian-architecture)
- **obsidian-mind** (`breferrari/obsidian-mind`, GitHub template vault): built specifically to give coding agents (Claude Code, Codex, Gemini CLI) "persistent, compounding memory"; uses event-driven agent hooks rather than manual context loading, bundles an MCP server for cross-repo access, and has an optional QMD semantic-search integration — [Obsidian Mind docs](https://docsearch.algolia.com/mcp/docs/repo/breferrari/obsidian-mind), [blog review](https://themenonlab.blog/blog/obsidian-mind-persistent-memory-ai-coding-agents)
- **AgentCairn** (`ccf/agentcairn`, Python, Apache-2.0, installed via `uvx agentcairn`): stores memory as human-readable Markdown with frontmatter and `wikilinks`, with a rebuildable DuckDB index (`cairn reindex`) layered on top for retrieval; ships an Obsidian community plugin giving a **read-only** graph/list view of agent memories with provenance — the plugin itself never writes to the vault — [PyPI agentcairn](https://pypi.org/project/agentcairn/0.24.1/), [Obsidian community plugin page](https://community.obsidian.md/plugins/agentcairn). Note: one directory listing shows only ~16 GitHub stars, suggesting this is a small/early project, not a widely adopted standard.
- **vault-memory** (`@owrede/vault-memory`, npm): runs locally, exposes search/note-writing/graph-navigation to any MCP-compatible agent; search combines semantic + full-text + hybrid methods; memory writes are labeled and provenance-tracked so user notes are never modified silently — [search result citing glama.ai listing]
- **OMPA** (PyPI `ompa`): three-layer design — plain markdown vault, a "palace" layer for structured metadata, and a temporal knowledge graph in SQLite on top; targets Claude Code, Codex, and LangChain agents; self-reports 96.6% R@5 on the LongMemEval benchmark (self-reported, not independently verified) — [PyPI ompa](https://pypi.org/project/ompa/)
- **Obsidian MCP** (self-hosted, by maxkuminov): backs the vault with PostgreSQL + pgvector and pluggable embeddings (Ollama or OpenAI); pitched on agents picking up the vault's existing folder layout, frontmatter schema, and tag conventions automatically on first call — [Glama listing](https://glama.ai/mcp/servers/maxkuminov/obsidian-mcp)
- **Vulcanus**: builds a Git-versioned, linked-markdown memory vault, can retrofit memory structure onto an existing Obsidian vault, and serves it over MCP — [search result]
- **Smart Connections** (`brianpetro/obsidian-smart-connections`, community plugin, ~4-5k GitHub stars as of mid/late 2026 by different sources): uses local embeddings (default model `TaylorAI/bge-micro-v2`, 384-dim, stored in a `.smart-env/` folder in the vault) to power a "Connections" view (semantically related notes) and a "Lookup" view (semantic search); its "Smart Chat" feature lets you converse with retrieved notes as context, supporting local models via Ollama/LM Studio or cloud APIs (OpenAI, Gemini, Claude) — [Smart Connections docs mirror](https://docsearch.algolia.com/mcp/docs/repo/brianpetro/obsidian-smart-connections)
- Caveat on Smart Connections: one review reports the plugin changed its license from GPLv3 to a source-available "Smart Plugins License" in early 2026 (single-source claim, not independently confirmed); a GitHub issue reports local embedding computation can interfere with normal vault use while it runs — [GitHub issue #559](https://github.com/brianpetro/obsidian-smart-connections/issues/559), [promptquorum review]
- Comparative note: in one scored review, Copilot for Obsidian ranked higher overall for "chat with your vault," while Smart Connections was rated best specifically for automatically surfacing related notes without prompting — [wetheflywheel.com Obsidian AI plugins radar](https://wetheflywheel.com/en/radar/obsidian-ai-plugins/)

### Inferences
- Given the user's existing vault already has a human/machine split, daily-note activity log, and a routing table (very similar in spirit to MindStudio's `_agent/` + tiered-memory pattern), the most directly transferable technique is the **working → episodic → semantic memory tiering with a scheduled consolidation pass** — this maps cleanly onto "daily note Activity log" (working/episodic) → periodic summarization into `Machine/Workflows/*/FINDINGS.md`-style semantic notes, which the vault's AGENTS.md already gestures at ("after running a workflow, record what you learned").
- For token efficiency specifically, the repeated theme across sources is: avoid embeddings/vector search as the default retrieval path for an agent-driven vault (most working implementations use plain keyword/path search), and instead rely on **fixed folder structure + consistent frontmatter fields** to let the agent narrow scope before reading file bodies. Embedding-based plugins (Smart Connections, Obsidian MCP w/ pgvector) exist and are real, but are oriented more toward human semantic browsing/chat-with-notes than toward minimizing a coding agent's token spend.

### Gaps
- No documented case study was found of embedding-based retrieval (e.g., Smart Connections or pgvector-backed Obsidian MCP) being measured specifically for *token efficiency* in an agentic workflow — the token-efficiency techniques found are all from the keyword/frontmatter-based MindStudio approach, not the embedding-based tools.
- Could not verify current GitHub star counts / maintenance status for vault-memory, OMPA, Vulcanus, or Obsidian MCP (maxkuminov) directly from their repos — only secondary directory/listing pages were available in search results, so treat adoption levels for these as unverified and possibly small/early-stage.
- No official Obsidian team or modelcontextprotocol.io documentation specifically endorses any one of these approaches — all are community projects of varying maturity.

## What repo/file-structure conventions are considered best practice for making a codebase easier for coding LLM agents to navigate — cite real examples

### Takeaway
Two complementary, now well-established conventions exist: **AGENTS.md** (an open, tool-agnostic standard for a markdown file of agent instructions, stewarded by the Agentic AI Foundation under the Linux Foundation, read natively by most major coding agents) and **CLAUDE.md** (Claude Code's own file, same idea, with detailed official guidance from Anthropic on what to include/exclude). Both converge on the same principle: keep the file short, put only non-obvious/non-discoverable information in it, and use nested files per-subdirectory for monorepos rather than one giant root file. `llms.txt` is a related but distinct, more contested convention for whole-*website* navigation, not repo structure, and is explicitly unconfirmed as actually used by major AI providers.

### Cited Findings
- **AGENTS.md** is described on its own site as "a README for agents," used by over 60,000 open-source projects; it is a plain markdown file kept separate from the human-facing README; no required fields/schema; stewarded by the Agentic AI Foundation under the Linux Foundation, having emerged from collaboration between OpenAI Codex, Amp, Google's Jules, Cursor, and Factory — [agents.md](https://agents.md)
- Nested-file behavior: subprojects can have their own `AGENTS.md`; agents read the **nearest** file in the directory tree, which takes precedence over a root-level file; explicit user chat instructions override both. Example cited: the OpenAI Codex repo itself had 88 such nested AGENTS.md files at time of writing — [agents.md](https://agents.md)
- Tools that read AGENTS.md natively (per the spec site): Codex, Jules, Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, Junie, Amp, Cursor, RooCode, Gemini CLI, Kilo Code, Phoenix, Semgrep, GitHub Copilot's coding agent, Ona, Windsurf, Augment Code; example adopting repos: `openai/codex`, `apache/airflow`, `temporalio/sdk-java`, `PlutoLang/Pluto` — [agents.md](https://agents.md)
- Migration/config notes: Aider needs `read: AGENTS.md` added to `.aider.conf.yml`; Gemini CLI needs the context filename set to AGENTS.md in `.gemini/settings.json`; teams can migrate existing docs by renaming to AGENTS.md and symlinking the old filename for backward compatibility — [agents.md](https://agents.md)
- Effectiveness evidence is mixed and should be flagged as such: one OpenAI-linked study found agents finished faster with an AGENTS.md present; a follow-up found LLM-*generated* AGENTS.md files slightly reduced task success while increasing cost ~23%, whereas human-written files improved success by about 4% — the inference offered is that human-written files help mainly when they contain genuinely non-discoverable information, while auto-generated files tend to just restate what the agent could already find by reading code — [search synthesis citing morphllm.com and addyosmani.com]; a separately-cited "35–55% reduction in agent-generated bugs" statistic from a Substack post is explicitly flagged by that same search as dubious/unverified and should not be treated as reliable.
- **CLAUDE.md** (Anthropic's own file, same underlying idea as AGENTS.md but Claude-Code-specific): per Anthropic's official docs, it is "a special file that Claude reads at the start of every conversation," with **no required format**, meant to stay short and human-readable — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Official example content from Anthropic's docs:
  ```markdown
  # Code style
  - Use ES modules (import/export) syntax, not CommonJS (require)
  - Destructure imports when possible (eg. import { foo } from 'bar')

  # Workflow
  - Be sure to typecheck when you're done making a series of code changes
  - Prefer running single tests, and not the whole test suite, for performance
  ```
  — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Official include/exclude table from Anthropic: **Include** — bash commands Claude can't guess, code style rules that differ from defaults, testing instructions/preferred test runners, repository etiquette (branch naming, PR conventions), architectural decisions specific to the project, developer environment quirks (required env vars), non-obvious gotchas. **Exclude** — anything Claude can figure out by reading code, standard language conventions, detailed API docs (link instead), information that changes frequently, long tutorials, file-by-file descriptions, self-evident practices like "write clean code" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Explicit heuristic given by Anthropic: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" — and if a rule keeps getting ignored, the fix is usually to shorten the file, not add more emphasis; emphasis (e.g. "IMPORTANT") should be reserved for a single standout line, because emphasizing many lines makes none of them stand out — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Monorepo nesting is explicitly supported for CLAUDE.md too: "For monorepos, you might run claude from root/foo, and have CLAUDE.md files in both root/CLAUDE.md and root/foo/CLAUDE.md. Both are then loaded automatically" (per third-party summary of Anthropic's guidance) — [search synthesis]; Anthropic's own current docs additionally note CLAUDE.md files "can import additional files using `@path/to/import` syntax" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices) → see [CLAUDE.md memory docs](https://code.claude.com/docs/en/memory.md)
- Anthropic recommends treating CLAUDE.md like code: check it into git so the whole team contributes and it "compounds in value over time"; review/prune it when things go wrong; for domain knowledge that's only sometimes relevant, use a **Skill** (`.claude/skills/<name>/SKILL.md`) instead of bloating CLAUDE.md, since skills load on demand rather than every session — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Named common failure pattern directly relevant to repo-structure docs: "The over-specified CLAUDE.md" — if the file is too long, Claude ignores half of it because important rules get lost in noise; fix is to ruthlessly prune, deleting anything Claude already does correctly without the instruction (or converting it to a deterministic hook instead) — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- `llms.txt` is a **separate, website-level** (not repo-level) convention: a markdown file at a site's root (`/llms.txt`) proposed by Jeremy Howard of Answer.AI in September 2024, giving an H1 title, blockquote summary, and H2-organized links to important pages, with a community extension `/llms-full.txt` that concatenates full docs into one file. It is explicitly **not** an access-control mechanism (unlike robots.txt) and sensitive content still needs real auth — [joinmassive.com glossary], [promptmetheus.com glossary]
- Adoption of llms.txt is contested: one source quotes Google's John Mueller saying "no AI system currently uses llms.txt," and Google has stated it isn't used for AI Overviews/AI Mode; a conflicting SEO-agency glossary claims adoption "across Anthropic Claude, Cursor, MCP tooling" but this could not be verified against any primary source and directly conflicts with the Google statement — flagged as an open contradiction, not resolved — [Chrome DevRel / Lighthouse docs on llms.txt](https://developer.chrome.com/docs/lighthouse/agentic-browsing/llms-txt), [georadar.tenten.co glossary]
- Separately, Anthropic's own Claude Code documentation site publishes its own `llms.txt`-style index at `https://code.claude.com/docs/llms.txt` as a "Documentation Index" for discovering all doc pages — this is a first-party, confirmed real-world usage of the llms.txt pattern, even though it's unclear whether other AI systems consume it — [observed directly via WebFetch of code.claude.com/docs/en/best-practices, which returned this index pointer]

### Inferences
- The two conventions (AGENTS.md and CLAUDE.md) are functionally the same pattern — a short, curated, human-written "onboarding doc for an agent," checked into git, with nested per-directory overrides for monorepos — just standardized under different stewardship (cross-vendor Linux Foundation effort vs. Claude-Code-specific). A project targeting multiple coding agents (Codex, Cursor, Claude Code, etc.) would do best with a root `AGENTS.md` and could symlink `CLAUDE.md -> AGENTS.md` for Claude Code compatibility, per the migration guidance found.
- The research-backed caveat that LLM-*generated* AGENTS.md files perform worse than human-written ones is directly relevant to any workflow where an agent is asked to auto-generate or maintain its own AGENTS.md/CLAUDE.md — it suggests a human should review and prune such files rather than letting an agent freely expand them, which aligns with Anthropic's own "ruthlessly prune" guidance.
- `llms.txt` is not a repo-structure convention and should not be conflated with AGENTS.md — it is for whole-website content indexing aimed at general-purpose LLM consumers, with disputed real-world adoption, whereas AGENTS.md/CLAUDE.md are specifically for coding-agent repo navigation and have confirmed, extensive adoption (60k+ projects, major CLI tools).
